# CAL-076 · Cobrança: assinatura, extras e checkout (mock agora, Stripe depois)

Plano guarda-chuva do Sprint 7. Cobre **CAL-076** (checkout), **CAL-077** (eventos de pagamento),
**CAL-078** (upgrade/downgrade), **CAL-080** (tela de assinatura) e **CAL-115** (extras pagos no
plano). Decidido com o Victor em 2026-11-15. **Uma fase por sessão**, na ordem abaixo.

## Decisões (valem para todas as fases)

1. **Gateway: Stripe** (CAL-075 decidido). A implementação real do Stripe é a **última fase** e
   espera a conta do Victor. Até lá tudo roda com o provedor **mock**, e o resto do sistema não
   sabe qual provedor está em uso.
2. **Interface única** em `src/lib/billing` (CLAUDE.md §2). `BILLING_PROVIDER=mock | stripe`.
   Página, action, webhook e cron só falam com a interface e com eventos **normalizados** (nunca
   com tipos do Stripe).
3. **Mock = pagamento simulado que sempre aprova.** O checkout abre
   `app.*/pagamento-simulado/{sessionId}` com o resumo (plano, extras, total) e um botão
   **"Aprovar pagamento"**. Aprovar gera os mesmos eventos normalizados que o webhook do Stripe vai
   gerar (`checkout.completed` → `invoice.paid`). Serve para criar contas de teste. Recusa, atraso e
   renovação só se simulam pelo `/admin` (botões visíveis só com `BILLING_PROVIDER=mock`).
   - Em produção o provedor é `stripe`. Para conta de teste/cortesia em produção: botão
     **"Ativar sem cobrança (cortesia)"** no `/admin` (status `active`, `subscriptions.provider =
     'manual'`, registrado no `admin_audit_log`).
4. **Preços no banco, versionados.** Tabela única `billing_prices` para planos e extras. Preço
   nunca é editado: mudar o valor cria uma linha nova e marca como atual (igual ao Stripe, onde
   `Price` é imutável). **Quem já assina mantém o preço antigo** (cada item da assinatura aponta
   para o `price_id` que contratou). O admin tem a opção explícita "aplicar também a quem já
   assina" (vale a partir do próximo ciclo, sem cobrança proporcional).
   - `src/lib/plans.ts` continua sendo a fonte dos **recursos** de cada plano; `priceCents` vira
     só o valor inicial do seed e fallback se o banco não responder.
   - Landing (`(site)/page.tsx`), cadastro, onboarding e `/assinatura` passam a ler o preço atual
     do banco (`getCurrentPrices()`, cache curto).
5. **Extras (add-ons) = itens da assinatura**, com quantidade:
   - Catálogo em `billing_addons` (o que o extra faz) + preço em `billing_prices`.
   - Extras de cada negócio em `business_addons` (quantidade, preço travado, valor livre opcional).
   - No Stripe cada extra é um *subscription item* (`price` + `quantity`). Adicionar/remover no
     `/admin` atualiza a assinatura **com cobrança proporcional** e a próxima fatura já vem certa.
   - Extras iniciais (seed): **"+100 mensagens/mês"** (R$ 10,00, `kind = messages`,
     `unit_amount = 100`) e **"+1 pessoa na equipe"** (R$ 5,00, `kind = members`,
     `unit_amount = 1`). Também existe o tipo **`custom`** (valor e descrição livres, sem efeito em
     limite), para combinados fora do catálogo.
   - Quais planos aceitam cada extra: `billing_addons.plans text[]`. Pessoa extra não aparece no
     Pro+ (já é ilimitado).
6. **Limite efetivo** (substitui só a soma; os overrides do CAL-113 continuam):
   `limite = (override ?? padrão do plano) + extras`. O override segue sendo o ajuste manual da
   Calenvia (cortesia/caso especial); o extra é o que é cobrado. Para os helpers de `plans.ts`
   continuarem puros, o banco mantém em `businesses` duas colunas calculadas: `addon_messages` e
   `addon_members` (somadas por `recompute_business_addons()`, só o servidor escreve, mesma regra
   de privilégio por coluna de `plan`/`plan_status`).
7. **Status** (`businesses.plan_status`, já existe):
   - `pending`: cadastrado, sem pagamento. **Deixa de liberar recursos**: o painel leva para
     `/assinatura/checkout` e a página pública fica "indisponível". (Hoje `pending` conta como uso
     em `USABLE_PLAN_STATUSES`; isso muda na fase 2. Conferir seed e demo antes: precisam ficar
     `active`.)
   - `active`: pago. `past_due`: fatura falhou, continua funcionando por **7 dias**
     (`PAST_DUE_GRACE_DAYS` em `src/lib/billing/status.ts`). Depois vira `suspended` (painel só
     leitura + `/assinatura`, página pública fechada). Pagou → `active`.
   - `canceled`: no fim do período pago. Dados ficam; voltar a assinar reativa.
   - Transições numa função pura `nextPlanStatus(atual, evento, agora)`, 100% testada.
8. **Trocar de plano**: upgrade **na hora**, com cobrança proporcional. Downgrade **no fim do
   ciclo** (sem reembolso). Extras que o plano novo não aceita saem junto. Se a equipe ficar acima
   do limite, ninguém é removido: só bloqueia novos convites (já é o comportamento de
   `canAddMember`).
9. **Cancelar**: sempre no fim do período (`cancel_at_period_end`).
10. **Teste grátis (CAL-079): ainda não decidido.** Padrão até o Victor decidir: **sem teste**.
    Deixar `TRIAL_DAYS = 0` em `src/lib/billing/config.ts`; se virar > 0, o checkout cria a
    assinatura com `trial_end` e status `active` (ou um `trialing` a decidir).
11. **Pix**: começar com **cartão** recorrente. Pix em assinatura no Stripe Brasil precisa ser
    conferido na fase do Stripe; se não der recorrente, Pix entra como pagamento avulso de fatura.
12. Webhook **idempotente**: todo evento vai para `billing_events` (`provider` +
    `provider_event_id` único) antes de ser aplicado; repetido = ignorado.
13. Dependência nova só na fase 6: pacote `stripe` (oficial). Já aprovado pelo Victor ao escolher o
    Stripe; nenhuma outra.

## Modelo de dados (fase 1)

Migration nova `supabase/migrations/2026111x_billing.sql`. RLS ligado em tudo; escrita só pelo
servidor (service role); dono e gerente leem o que é do próprio negócio (`has_perm(...,
'billing.view')` ou permissão equivalente; conferir a matriz em `src/lib/permissions.ts` e em
`public.has_perm()`, que precisam continuar espelhadas).

- **billing_addons**: id, code (único, ex.: `extra_messages_100`), name, description, kind
  (`messages` | `members` | `custom`), unit_amount int null, plans text[], is_active, sort_order,
  created_at.
- **billing_prices**: id, product (`plan` | `addon`), plan text null (`basic` | `pro` |
  `pro_plus`), addon_id null → billing_addons, amount_cents int > 0, currency `brl`, interval
  `month`, provider_price_id text null (Stripe; null no mock), is_current bool, created_at,
  created_by. Check: plan xor addon. Índice único parcial: um `is_current` por plano/extra.
- **subscriptions** (já existe): acrescentar `price_id` → billing_prices (plano), `provider_item_id`
  (item base no Stripe), `cancel_at_period_end bool`, `pending_plan` (downgrade agendado),
  `trial_end`, `past_due_since`. Índice único parcial: uma assinatura não cancelada por negócio.
  `provider` aceita `mock` | `stripe` | `manual`.
- **business_addons**: id, business_id, addon_id, price_id, quantity int > 0,
  custom_amount_cents null (só `custom`), custom_label null, provider_item_id null, note,
  created_by, created_at, removed_at null. Único parcial `(business_id, addon_id) where removed_at
  is null` (exceto `custom`, que pode ter vários).
- **invoices**: id, business_id, provider, provider_invoice_id único, amount_cents, status (`open` |
  `paid` | `failed` | `void`), period_start, period_end, paid_at, hosted_url null, lines jsonb
  (descrição, quantidade, valor de cada item), created_at.
- **checkout_sessions**: id, business_id, provider, provider_session_id, plan, price_id, addons
  jsonb, status (`open` | `completed` | `expired`), created_at, completed_at.
- **billing_events**: id, provider, provider_event_id, type, payload jsonb, business_id null,
  received_at, processed_at, error. Único `(provider, provider_event_id)`.
- **businesses**: `addon_messages int not null default 0`, `addon_members int not null default
  0`; privilégio de coluna igual a `plan`.
- Funções (security definer, `set search_path = ''`, EXECUTE só `service_role`):
  `recompute_business_addons(p_business_id)` e `current_prices()`.
- Seed: preços atuais dos 3 planos (de `plans.ts`), os 2 extras iniciais, seed/demo com
  `plan_status = 'active'` e assinatura `manual`.

## Interface (fase 2)

`src/lib/billing/`:
- `types.ts`: `BillingEvent` normalizado (`checkout.completed`, `invoice.paid`,
  `invoice.payment_failed`, `subscription.updated`, `subscription.canceled`), `DesiredItems`
  (plano + extras com quantidade).
- `provider.ts`: `interface BillingProvider { createCheckout; syncItems; changePlan; cancel;
  resume; customerPortalUrl?; parseWebhook(request) }` e `getBillingProvider()` por
  `BILLING_PROVIDER`.
- `mock.ts`: grava `checkout_sessions`/`invoices` no banco e emite eventos chamando o mesmo
  `applyBillingEvent`. Ids `mock_...`.
- `stripe.ts`: **só na fase 6**.
- `events.ts`: `applyBillingEvent(event)` (idempotência via `billing_events`, atualiza
  `subscriptions`, `businesses.plan/plan_status`, `invoices`, `product_events`).
- `status.ts`: `nextPlanStatus`, `PAST_DUE_GRACE_DAYS`. `prices.ts`: `getCurrentPrices()`,
  `subscriptionTotal(items)` (pura). `config.ts`: `TRIAL_DAYS`.
- Rota `src/app/api/webhooks/billing/route.ts` (pasta já existe com `.gitkeep`): chama
  `provider.parseWebhook` → `applyBillingEvent`. No mock, recusa tudo (o mock não usa webhook).
