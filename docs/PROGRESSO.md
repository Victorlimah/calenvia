## Decisões tomadas
- Repositório git iniciado localmente (`git init`, branch `main`). Commits usam o `user.name`/`user.email` já configurados no git global da máquina.
- Docker Desktop foi iniciado (`systemctl --user start docker-desktop`) para rodar o Supabase local.
- Next.js 15 (não 16) porque o CLAUDE.md fala em `middleware.ts` (no 16 virou `proxy.ts`).
- Supabase CLI instalado como devDependency (`npx supabase`), sem instalação global.
- Dev usa Supabase local (`npx supabase start`). O arquivo `.env.local` (ignorado pelo git) tem as chaves públicas de demonstração do Supabase local.
- Status/plano/tipo em colunas text com CHECK (não enums), mais fácil de evoluir. FKs compostas (id, business_id) garantem que serviço/profissional/cliente de um agendamento são do mesmo negócio.
- Colunas extras: businesses.message_limit_override (uso justo do Pro+ por negócio), businesses.onboarding_completed_at, plan_status com 'pending' (padrão até o pagamento). Índice único impede dois lembretes por agendamento. Slug com 3 a 40 caracteres.
- Dono não pode alterar plan/plan_status (privilégio por coluna); só o servidor (service_role) muda isso.
- Testes de banco (RLS etc.) ficam em tests/db e rodam com `npm run test:db` contra o Supabase local; no CI há um job `db` que sobe o Supabase. `npm test` continua só com testes unitários (rápido, sem Docker).
- Roteamento por host: app.* é reescrito para /painel/*, {slug}.* para /{slug}/*. O middleware injeta x-calenvia-host/x-calenvia-slug e os layouts dão 404 se a rota for aberta pelo host errado (ex.: calenvia.com.br/barbearia-do-ze). Todo login/cadastro fica no host do painel (app.*), para não depender de cookie entre subdomínios.
- Ordem: CAL-017 (design system) foi feito antes do CAL-026 (autenticação), porque as telas de login já precisam dos componentes. CAL-022 (deploy) é preparado sem deploy (proibido no modo autônomo).
- Playwright usa o Google Chrome já instalado (`channel: chrome`), sem baixar navegadores. Testes E2E em tests/e2e (`npm run test:e2e`), precisam do Supabase local com seed.
- Server actions NÃO usam redirect() para caminhos internos: o redirect da action é resolvido sem passar pelo middleware (rewrite por host) e cai na rota errada (/[slug]). As actions devolvem { redirectTo } e o cliente faz router.push.
- Um negócio por conta no MVP (getCurrentBusiness pega o primeiro do dono). Salvar horários e serviços do profissional usa funções SQL atômicas (save_business_hours, set_staff_services) com RLS (security invoker).
- Tabela extra business_photos (galeria 'fotos do trabalho', até 12 fotos) — não estava na seção 4 do CLAUDE.md, mas a página pública precisa. Imagens no bucket público business-media/{business_id}/{tipo}/; compressão no navegador para WebP.
- Tabela extra business_testimonials (depoimentos cadastrados pelo dono, até 10) para a seção de depoimentos da página pública.
- Motor de horários: os intervalos do negócio (almoço) valem para todos os profissionais, mesmo os com horário próprio. Dia com horário mas sem nenhum livre = status 'full' (além de closed/past/too_far/no_staff).
- src/lib/plans.ts criado já no Sprint 4 (a página pública precisa de canSendAutomaticMessages/canManageByLink). plan_status 'pending' (sem gateway ainda) conta como ativo; 'suspended'/'canceled' fecham a agenda pública.
- Página pública: 'Dúvidas' geradas automaticamente pelas regras do negócio (antecedência, cancelamento, confirmação conforme o plano). Seções sem conteúdo (fotos, depoimentos) não aparecem. Único link fora do CTA: 'Ver no mapa'.
- CAL-066 (conta Meta) é fora do código: pulado. Todo o WhatsApp fica pronto no modo mock (WHATSAPP_MODE=mock) e com o cliente da Cloud API para o modo live.
- Templates do WhatsApp: a Meta não aceita corpo terminando em variável, então os textos ganharam uma linha final ('Até lá!', 'Te esperamos!', 'Obrigado!'). O texto da prévia/wa.me é gerado a partir do mesmo corpo do template (fonte única).

- Remarcar reenvia a confirmação (com o novo horário); cancelar pelo painel envia o template de cancelamento. Erros de envio só vão para o log, nunca desfazem o agendamento.
- /assinatura criada já no CAL-071 (o menu de Ajustes apontava para ela e o aviso de cota precisa de destino), só com plano, status, uso do mês e a lista de planos. Faturas e trocar/cancelar ficam no CAL-080.
- increment_message_usage (migration inicial) não é mais usado no envio; foi mantido por compatibilidade.
- Janela do lembrete (não estava definida no CLAUDE.md): 24 h antes; quem agenda com menos de 24 h recebe 2 h antes; com menos de 4 h não há lembrete. Constantes em src/lib/whatsapp/reminders.ts, fáceis de mudar.
- E2E ajustes.spec.ts passou a limpar o profissional "Bruno Teste" (sobrava no seed e quebrava o teste de banco de "sem preferência").
- Opt-out sem contexto (cliente manda SAIR sem responder a uma mensagem) vale para todos os negócios daquele número, porque o número que envia é o mesmo da Calenvia. A Calenvia ainda não responde "você não vai mais receber" ao cliente (precisaria de mensagem de texto livre na janela de 24 h; fica para depois).
- Rodapé de opt-out entrou nos templates v1 (ainda não cadastrados na Meta, então não precisou de v2).
- Victor autorizou (2026-11-14) pular o Sprint 7 (bloqueado pelo CAL-075) e seguir o backlog até o fim. Cards que dependem do gateway ou de decisão dele ficam registrados em Bloqueios.
- Realtime: o canal só recebe eventos se for autenticado com o token do dono (setAuth antes de assinar); sem isso o RLS bloqueia em silêncio.
- Lighthouse não pôde ser baixado (npx bloqueado pelas permissões). A meta do CAL-053 foi verificada com axe-core (já instalado, agora em devDependencies) e pelo tamanho dos bundles do build. Rodar o Lighthouse manualmente no deploy de preview.
- Sem serviços externos novos: monitoramento (CAL-029) e métricas (CAL-085) são próprios; Sentry/Plausible/PostHog podem entrar depois com aprovação do Victor.
- Rate limit não se aplica a 127.0.0.1 em desenvolvimento (os E2E fazem muitas chamadas); RATE_LIMIT_LOCAL=1 liga localmente.
- LGPD: apagar dados de um cliente anonimiza (não remove linhas), para o faturamento do dono continuar certo. O número vira 5500xxxxxxxxx (DDD 00 não existe).
- Suíte E2E: uma falha intermitente apareceu numa rodada completa e não se repetiu com o mesmo código (60/60 na rodada seguinte).
- CAL-111: dono e gerente editam os ajustes de mensagens (settings.manage, CAL-112). Lembrete desligado no negócio não gera registro skipped (evita ruído).
